# CRAC rework ToOp

State: draft
Author: Nico Westerbeck
Opened: 26.09.2026

This document describes a high level rework of the ToOp CRAC format including visions to move closer to the powsybl APIs.

## Motivation, current state

When we started the project, we assumed area-wise settings, i.e. that we do not get a list of N-1
cases, actions, monitored items, etc but just areas in which we monitor everything and can
switch everything. While this approach led us to deliver results early without large configuration
requirements, it proves difficult in an operational perspective, where very precise configuration
is paramount. The aim of this proposal is to deliver a long, medium and short term view on how
to structure the (***C***ontingency list, ***R***emedial ***A***ctions and additional ***C***onstraints) CRAC definition
for ToOp.

Interestingly, OpenRAO did exactly the opposite. Instead of defining catch-all CRACs, they
require an in-depth definition of every pair of outaged element, monitored element together with
their limits set. This results in very large crac files that tend to work only on the specific date
they were intended for, even if customizability is maximal.

The long term vision would be, in collaboration with the ORAO team, to build a holistic API with
just the right degree of customizability, but such that it is not necessary to build a crac file for
every single optimization run and instead reuse it across multiple runs. Purely autogenerated is
not working, fully defining every single co/cb/limit case is also not working.

DSO Trafos: Their initial loadflow loading (N-1) is set as an artificial limit for the optimization.
There is a penalty when the flow is increased above that, but no bonus for reducing it.

Lightly loaded elements: Elements which are, pre-optimization, below their operational limit (e.g.
<100%) shall receive a penalty once they move upwards in a defined double limit band (e.g.
90%).

Different limits for Redispatch vs Topology: It might be fundamentally thinkable to assign
different limits to the topology part vs redispatch. However, this would add another layer of
complexity and we currently assume that all limits that hold for ToOp will also hold for ORAO.

TATL/PATL: This proposal is not formulated for TATL yet, everything only holds for PATL.

## Terminology

- **Optimized element**: A grid element that, if it exceeds a limit, should be healed to be below the
  limit after the optimization
- **Monitored element:** (do-not-make-worse) A grid element that should not be healed if it is
  above its limit, but should also not be pushed even further above its limit. Something that is neither monitored nor optimized will not appear in the loadflow results.
- **CRAC:** ***C***ontingency list, ***R***emedial ***A***ctions and additional ***C***onstraints - basically all the configs that go into ToOp
- **Double limit:** Every monitored and optimized element can have a double limit. In the case that
  the element was below limit before the optimization, a buffer zone below the actual limit is
  introduced to keep it safely away from that limit post-optimization.
- **Contingency cases:** The N-1 outage cases to be computed as part of the security
  assessment.
- **Artificial limit:** A limit that is determined based on the initial loadflow and either the double
  limit and monitored rules.
- **Generative CRAC API** An API that implements rule based, heuristic or any other logic to generate specific CRAC API files. E.g. switch everything in this grid area
- **Specific CRAC API** An API which describes exactly the actions available, including specific switching sequences and an ID for each entry. e.g. A single topological action including all operated switches and their target open/close state.



## Examples

- Element is optimized, not monitored (and double limit band from 90%)
  - \>100% → artificial limit it 100%
  - \>90%, <100 → double band logic sets artificial limit to exactly the loading
  - <90% → artificial limit 90%
- Element is monitored, not optimized
  - → artificial limit is exactly the loading
- Element is monitored and optimized
  - \>100% → artificial limit is 100%
  - <100% → artificial limit is exactly the loading
- Element is neither
  - → will not appear in optimization or results.

## Long Term Vision

Long term, we have a unified CRAC API for Topology/Congestion, Topology/Voltage,
Redispatch/Congestion and Redispatch/Voltage. Common aspects such as optimized/monitored
elements or outages share a format, while individual considerations such as degree of flexibility
of switching within the station can be defined use-case specific. The common API is the
enabler for flexibly chaining and reusing optimization solutions in different business use-cases.

For this, we envision a **"detail overwrites general rule"** setting, in which general rules (e.g.
areas) can be amended with specific details. An overwrite can conceptually alter, add or remove
an inferred rule. The "remove" part is especially tricky as the current ORAO Crac definition does
not have this capability.

## As-is state

Currently, in ToOp, we have area settings that define the areas for N-1, optimized elements and
where switching is possible. We can not take into account individual optimized elements outside
the area and we could not exclude from the areas. The exclusion problem has been solved
through the introduction of ignore lists, however these ignore lists are currently only ignoring
optimized elements.

From the area-settings, we translate within multiple steps towards the data formats required in
the DC and AC solver. The AC solver requires a N-1 definition json, which is first created in the
importing based on the area settings, but then reworked during preprocessing to reflect only
what is possible to compute in our DC solver at the moment. Furthermore, masks are created
that first reflect the area settings and then later the final N-1 cases in the DC and AC solvers.

Furthermore there is a naming conflict, "monitored" in ToOp terms means "optimized" in orao
terms.

## Step 1: Monitored/Observed rework

First step will be to remove view and n-1 areas from the importing and instead retain them as
helper scripts. The helper scripts are mostly aimed at people starting with ToOp and just want to
optimize any grid file. Instead, the importing will only look at the business N-1 definition.

The format-specific translations will live in the ingress, and the ingress will translate to business
N-1 definion json format. E.g. the belgian N-1 format will be translated by the ingress towards
business N-1 json. For the UCTE/CGMES merge, we will likely still have area definitions and will
use the scripts as part of the ingress, creating a business N-1 file.

In general, the view on our ingress should be that it transforms all data into the format that the
internal engine expects, instead of forcing the engine format to honor arbitrary csv formats.

The N-1 format thus has to hold information about monitored, optimized and double limits. The
double limit band may be stored per-element.

When displaying results for alternative limits, we should find a UI concept. It is not intuitive to
just adjust the limit in the display and claim a monitored item sits at 100%, while it actually is at
125%, even though for our optimizer this is the case. One option would be a toggle (i.e. show
"natural" load vs artificial), however in the artificial load scenario we would see a lot of elements
around 100% (everything that is monitored or in the double limit band). We could also add a
toggle for "optimized" only, which would make these odd trafos disappear that we have
currently. Then, we should still answer how we display the double band logic. 

To be able to convey these thoughts, we would require the option of adding multiple types of
limits. Currently, loading is a property that is hard-coded into the loadflow results. This will not
scale with multiple artificial limits. I.e. we should generate the loading value on-the-fly and
potentially drop it from the loadflow result interface.
